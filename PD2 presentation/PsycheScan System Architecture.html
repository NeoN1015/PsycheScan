01

System at a glance

PsycheScan screens a participant for stress and anxiety by combining two independent evidence streams. A device measures four vital signs (heart rate, skin conductance, peripheral temperature, and motion) and an ESP32 microcontroller streams them to the dashboard. A USB webcam supplies the face, which a convolutional neural network (CNN) reads for emotional expression while an image-analysis routine estimates visual fatigue. The dashboard fuses both streams into one Integrated score on a four-level scale (Minimal, Mild, Moderate, Severe), and an LSTM network reports the sustained trend of the vital signs over the last minute.

All processing runs locally on the mini PC. The dashboard is a web application that runs in the browser; a small Python server stores patients, records, and reports in a SQLite database on the same machine.

02

Device and firmware

The ESP32 runs a cooperative loop that reads each sensor at its own rate, checks that the sensors touch the skin, and sends the latest values every 500 ms. The device only measures; every severity decision is made by the dashboard (Section 06), so the thresholds live in one place.

Every 500 ms the same line of JSON goes out on all three links at once: USB serial (115200 baud), Bluetooth LE (device name ESP32_StressMon, Nordic UART service), and a Wi-Fi WebSocket server on port 81. When a sensor has no skin contact its value is sent as 0 with its contact flag set to false, and the dashboard discards it. The on-board LED toggles once per second to show the device is running.

03

Sensor data intake

The dashboard accepts the same JSON packet through any of three transports, or generates demo values for practice sessions. Every packet passes through the same normalization and validation before it can influence a score.

Transports

  • Wi-Fi WebSocket: connects to the ESP32 at the configured URL (default ws://10.73.86.82:81). On disconnect it retries after 1 s, doubling up to 30 s.
  • Bluetooth LE: Nordic UART service 6e400001-…, notifications on 6e400003-…; partial lines are buffered until a newline.
  • USB serial: Web Serial at 115200 baud, one JSON object per line.
  • Demo sensors: only when no transport is connected; every 2 s random HR 60–85 bpm, GSR 0.9–1.1 µS, temperature 33–35 °C, motion 0.05–0.20 g.

Validation rules

  • Field aliases are accepted: eda→gsr, temperature→temp, acc/accMag→motion, pulse→hr.
  • Contact flags (max30102, gsrConnected, ds18b20) mark the matching value as touching skin.
  • Valid ranges: HR 25–240 bpm, GSR 0–100 µS, temperature 15–45 °C, motion 0–16 g. Anything else, or no contact, clears the value.
  • A sensor not heard from for 6 s is cleared and shown as Waiting or Disconnected.
  • Packets longer than 8192 bytes are discarded.

04

Facial analysis (CNN)

The facial stream uses pretrained convolutional networks from the face-api.js library, running in the browser on the mini PC. On every detection tick the system finds one face, locates 68 facial landmarks, and classifies the expression into seven emotions.

ModelTypeRoleUsed when
SSD MobileNet V1Single-shot detector CNNFinds the face box (one face, minimum confidence 0.35)Detection profile "Strong" or "External Cam Strong" (the default)
Tiny Face DetectorLightweight detector CNNFinds the face box; input 320, 416, or 512 px (default 512)"Standard" profile (confidence 0.45), or if SSD cannot load
Face Landmark 68 NetCNN regressor68 points: eyes, brows, nose, mouth, jawEvery detected face
Face Expression NetCNN classifierProbabilities for neutral, happy, sad, angry, fearful, disgusted, surprisedEvery detected face

Model weights are loaded from the face-api.js model host or from the local models/ folder, whichever the Model source setting puts first; the other is the fallback. Raw expression probabilities are smoothed with an exponential moving average before use:

smoothed = smoothed × α + raw × (1 − α) α = 0.25 (low), 0.40 (balanced, default), 0.60 (strong) dominant emotion = the class with the highest smoothed probability; confidence = that probability × 100

When no face is found the emotion values reset to zero, the dominant emotion becomes "No Face", and the facial stream drops out of the Integrated score until a face returns.

  • main.js: smoothExpressions, getDominantExpression, drawDetection, restartDetectionLoop, stopCamera
  • models/: face-api.js weight files and manifests
05

Visual fatigue

Visual fatigue is measured from the pixels around the eyes, positioned by the 68 landmarks. Two cues are combined: darker skin under the eyes (eye bags) and extra fine texture on the forehead and eye corners (wrinkles), each compared against the cheek of the same person in the same frame so lighting differences cancel out.

  1. Brightness of each region is the mean luma: Y = 0.299 R + 0.587 G + 0.114 B.
  2. Texture of each region is the mean absolute luma difference between each pixel and its right and lower neighbours.
  3. The face must be large enough: average eye width at least 18 px. A detail factor scales scores down for small faces.
detail = clamp((eye width − 18) / 22, 0.15, 1) eyebag = clamp( clamp(cheek Y − under-eye Y, 0, 25) × 4.6 × detail, 0, 100) wrinkle = clamp( clamp(mean(forehead, eye-corner texture) − cheek texture, 0, 14) × 9.2 × detail, 0, 100) fatigue = 0.58 × eyebag + 0.42 × wrinkle (each then smoothed with the same α as emotions)

Each percentage is labelled with the facial bands: 0–24 Minimal, 25–49 Mild, 50–74 Moderate, 75–100 Severe.

Implemented in
  • main.js: computeVisualFatigue, sampleRegionLuma, sampleTextureScore, getBounds, getSeverityLabelFromPercent
06

Biomarker thresholds

Each vital sign is classified on its own using the validated thresholds (Table 1). Heart rate and GSR are judged two ways: by the absolute reading and by the percentage rise over the patient's captured baseline. The sensor takes the more severe of the two, so a participant with a low resting heart rate is still flagged when it climbs sharply. Temperature is judged as a drop, because peripheral skin temperature falls under stress; the drop comes from the device packet, otherwise from the captured baseline minus the current reading.

Reading the boundaries: a level's lower value counts as that level (86 bpm is Mild), and Severe begins strictly above the Moderate maximum (105 bpm is Moderate, 105.5 bpm is Severe). A rise of exactly +20 % in heart rate or +100 % in GSR stays Moderate. Percentage rules apply once the patient has a captured baseline.

The combined sensor level (shown as "Threshold" on the Dashboard and "ESP32 threshold stress" in the Status Summary) is a vote. Each sensor with valid skin contact casts a vote for its own level, GSR casting two. The most severe level that receives any vote becomes the sensor level; with no valid sensor it shows "Waiting for sensor".

07

Integrated score

The Integrated score is a weighted score-level fusion of three risks, each on a 0–100 scale. Only the streams that are present take part, and the weights are renormalised over them, so the score stays meaningful when the camera sees no face or when no sensor is connected.

emotion risk = clamp(100 × (sad + angry + fearful + 0.8 × disgusted + 0.35 × surprised), 0, 100) + 0.3 × confidence if the dominant emotion is Sad, Angry, Fearful or Disgusted (capped at 100) sensor risk = 0 (Minimal) · 33 (Mild) · 66 (Moderate) · 100 (Severe) from the sensor vote in Section 06 Integrated = (0.42·emotion + 0.18·fatigue + 0.40·sensor) ÷ (sum of the weights of the streams present)

Two temporal indicators are derived from the recent history of Integrated scores:

  • Trend: the average of the last 6 samples compared with the 6 before; a change above +4 is Rising, below −4 Falling, otherwise Stable.
  • Temporal stability: clamp(1 − variance / 900, 0.12, 0.97) over the last 6 samples, shown with a High, Medium, or Low label that follows the severity level.
Implemented in
  • main.js: computeAssessment, updateMetrics; weights in project_config.js → fusion; trend threshold runtime.trendDeltaThreshold
08

Temporal LSTM

The LSTM (long short-term memory) network adds the temporal half of the CNN-LSTM design. It reads the last 60 seconds of all four vital signs as a sequence and classifies the sustained level as Minimal, Mild, Moderate, or Severe. Because it looks at the whole minute, a brief spike such as a finger slipping off the pulse sensor does not change its answer, while the instant threshold level may flicker.

Input preparation

  • History samples are placed on a one-second grid; each second takes the latest complete reading, as long as it is at most 3 s old.
  • A prediction runs only when the oldest second is filled and at least 80 % of the 60 seconds have fresh readings. Until then the badge counts up, for example "16/60 S".
  • Values are normalised with the mean and standard deviation saved at training time.

Training

  • The current model is a bootstrap model trained on 16,000 synthetic 60-second sequences generated within the Table 1 ranges, with spikes, ramps, and noise.
  • Each sequence is labelled by the worst sustained level using the absolute Table 1 bands: the median of the last 30 s for HR, GSR, and motion, and the temperature decline across the window. The percentage rules need a patient baseline, so they are applied by the threshold level, not the LSTM.
  • It agrees with that rule on 91.3 % of held-out synthetic sequences. Retraining on labelled participant sessions uses the same architecture and replaces the model files.

The result appears on the Dashboard (badge "LSTM 60 s" beside "Threshold"), in the Status Summary ("LSTM sustained trend"), and in Settings with its confidence. It is reported alongside the Integrated score and is not part of its weighted mean.

09

Session workflow

Patient profiles

  • Each participant gets a profile identified by a name or code, which must be unique.
  • Profiles can be added, viewed, renamed, and deleted from Manage patients; deleting removes the profile's records, reports, and stored readings.
  • Monitoring and baseline capture require an active patient, so every reading is linked to one person.

Baseline capture

  • Length follows the Observation window: 3, 4, or 5 minutes, or a custom 1–60 minutes.
  • During capture the session is in the baseline phase; afterwards it moves to the questionnaire phase.
  • At the end the system stores averages of HR, GSR, temperature, and motion, the mean Integrated score, face detection rate, dominant expression, and the fatigue, wrinkle, and eyebag averages on the profile.
  • The baseline temperature becomes the reference for the temperature drop.

Live history and charts

  • A history sample (all sensor, face, and score values) is kept at the History sampling rate: 0.5, 1 (default), or 2 s.
  • Charts show a rolling 2-minute window, from −120 s to now.
  • A First reading delay (none, 10, 30, or 60 s) holds back history and records while the participant settles.

Records and reports

  • With Auto-capture on, a record is saved at most every 3 s when the face confidence is at least 30 % or a sensor is connected.
  • A record holds the time, patient, emotion and confidence, the four vital signs, eyebag, wrinkle, fatigue, Integrated score, level, and a short narrative; a matching report row is created.
  • Exports: CSV of all records, CSV per patient, and a printable PDF report with the charts.
Implemented in
  • main.js: startBaselineCapture, finalizeBaseline, getSessionPhase, pushHistory, getWindowHistory, exportCsv, savePdf
  • main_extension.js: addPatientProfile, updateActivePatient, deleteActivePatient, completeBaselineProfile, captureRecord, exportPatientCsv

Storage and server

Data lives in two places. The browser keeps a working copy so monitoring continues if the server is briefly unavailable, and the Python server keeps the permanent copy in SQLite.

EndpointPurpose
GET /api/auth-configTells the login screen whether sign-in is required (open to all)
POST /api/login · /api/logoutExchanges the operator password for a session token (valid 8 hours) and ends it
GET /api/bootstrapReturns settings, profiles, records, reports, session, per-patient face summaries, and the data revision
POST /api/syncSaves the full working state if the revision matches
POST /api/telemetryStores batches of history samples and records
POST /api/profiles/create · /update · /deletePatient management; names are unique regardless of letter case
GET /api/healthDatabase table and row counts

Access control

  • Secure mode: the operator sets a password when starting the server; any operator ID plus that password signs in.
  • The token is kept only in the current browser tab and sent with every API call.
  • After 5 failed sign-ins within 60 s an address is blocked briefly; at most 32 sessions are kept.
  • Requests must come from the same site that served the page, and request bodies are limited to 1 MB.
  • Local test mode skips sign-in but only accepts connections from the same computer.

Starting the system

  • start_server.bat checks for Python 3.10+, asks whether to use local test mode, and prompts for the operator password.
  • server.py copies the dashboard files into public/, prepares the database, and prints the address to open, for example http://localhost:8000.
  • Stored readings older than 30 days are removed at startup.

One session, start to end

  1. Operator · server

    Runs start_server.bat, sets the operator password, and opens the printed address. The server prepares the database and serves the dashboard.

  2. Dashboard · server

    The operator signs in; the dashboard loads all saved data from /api/bootstrap and the LSTM worker loads its model.

  3. Operator

    Selects or adds the participant on the Dashboard and fits the device.

  4. ESP32 · dashboard

    Sensors connect over Wi-Fi, Bluetooth, or USB. Packets arrive every 500 ms and are validated; sensor cards turn Connected.

  5. Dashboard

    Load Models and Start Camera: the face CNNs load and the detection loop begins (every 160 ms by default).

  6. Operator · dashboard

    Capture baseline: for the observation window the system collects the participant's resting values, then stores their averages on the profile.

  7. Dashboard

    Each packet and each detection tick recomputes the threshold level and the Integrated score, adds a history sample, and updates the charts.

  8. LSTM worker

    After 60 s of complete readings the LSTM reports the sustained level every 5 s.

  9. Dashboard · server

    Records are auto-captured and queued; sync and telemetry batches save everything to SQLite.

  10. Operator

    Reviews the Status Summary and the profile, then exports CSV or a PDF report. A qualified reviewer makes the final interpretation.
